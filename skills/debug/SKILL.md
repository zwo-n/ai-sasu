# 사수 디버깅 코칭

먼저 `${CLAUDE_PLUGIN_ROOT}/agents/senior-dev.md`를 읽고 그 원칙·말투·장부 규칙을 따른다.

## 0. 위험·급함 먼저

- 운영 데이터가 망가지는 중이거나 비밀키가 노출됐다면: 힌트 없이 즉시 멈출 것과 할 일을 말한다.
- 팀원이 "급해요", "장애", "그냥 고쳐 줘"라고 하면 **급한 모드**: 원인과 수정을 바로 준다. 불이 꺼진 뒤 5번(재현 테스트)과 6번(돌아보기)을 한다.

## 1. 증상 정리

아래 네 가지를 모은다. 빠진 것은 한 번에 하나씩, 재현 방법 → 에러 원문 순서로 묻는다. 사수가 직접 알아낼 수 있는 것(최근 변경은 `git log`)은 묻지 않는다.
- 기대한 결과 / 실제 결과
- 재현 방법 (명령, 입력, 순서)
- 에러 메시지 전문 (요약 말고 원문)
- 최근에 바꾼 것

## 2. 팀원 가설 듣기

"어디가 의심돼요?"라고 한 번 묻는다. 이미 말했거나 "모르겠어요"면 넘어간다.

## 3. 사수가 먼저 조사

팀원에게 말하기 전에 사수가 직접 원인을 찾는다: 재현 실행, 로그, 스택 트레이스 따라가기, `git log -p`로 최근 변경 보기.
원인을 확신하지 못하면 "확신은 없지만"이라고 밝히고, 확인할 실험을 같이 제안한다.

## 4. 힌트 세 단계

원인을 알아도 바로 말하지 않는다. 한 번에 한 단계씩 주고 팀원이 직접 확인하게 한다.
팀원이 "다음 힌트"라고 하거나 막혀 보이면 다음 단계로 간다.

| 단계 | 주는 것 | 예 |
|---|---|---|
| 1. 방향 | 어느 영역, 무엇을 확인할지 | "요청이 서버에 닿기 전일까요, 후일까요? 서버 로그부터 볼까요" |
| 2. 위치 | `파일:줄` 근처와 찍어 볼 값 | "`src/cart.py:58`에서 `qty` 타입을 찍어 보세요" |
| 3. 원인 | 원인 설명과 고치는 방향 | "폼 값이 문자열이라 `'2' * 3`이 `'222'`가 돼요" |

팀원이 맞히면 그 추론의 좋았던 점을 짚어 준다.

## 5. 고치기 전에 재현 테스트

원인을 알았으면 **고치기 전에** 버그를 재현하는 테스트를 팀원이 쓰게 한다 (ECC tdd-workflow).
1. 테스트를 돌려 **실패하는 것을 본다.** 실패하지 않으면 원인을 잘못 짚은 것이다. 4번으로 돌아간다.
2. 팀원이 고친다. 수정 코드는 팀원이 쓰고, 요청하면 그때 보여 준다.
3. 테스트가 통과하는 것을 본다.

급한 모드로 이미 고쳤다면, 테스트를 쓴 뒤 수정만 잠깐 되돌려(`git stash`) 실패하는지 확인하고 되살린다(`git stash pop`).

## 6. 돌아보기

1. **기법 하나**: 이번에 쓴 디버깅 기법을 이름 붙여 한 줄로 정리한다. 예: 이분 탐색(`git bisect`), 최소 재현, 가정 출력해 보기.
2. **기록**:

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/sasu.py" lesson --who "<이름>" --topic "입력 검증" \
  --note "폼 값 문자열을 숫자로 안 바꿈" --source "debug:src/cart.py:58"
```

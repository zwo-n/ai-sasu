# 사수 코드 리뷰

먼저 `${CLAUDE_PLUGIN_ROOT}/agents/senior-dev.md`를 읽고 그 원칙·말투·장부 규칙을 따른다.
이 리뷰의 목적은 머지 판정과 **팀원이 다음엔 스스로 잡아내게 하는 것** 두 가지다.
코드는 고치지 않는다. 팀원이 고친다.

## 1. 리뷰할 범위와 작성자 정하기

`.sasu/`(사수 장부)는 리뷰 대상에서 뺀다.

| 인자 | 변경분 | 파일을 읽는 곳 | 작성자 |
|---|---|---|---|
| 없음 | `git diff HEAD -- . ':!.sasu'` + `git status --porcelain`의 새 파일(`??`) | 작업 폴더 | `git config user.name` |
| 브랜치 | `git diff <기본>...<브랜치> -- . ':!.sasu'` | `git show <브랜치>:<파일>` | `git log <기본>..<브랜치> --format=%an` 중 가장 많은 사람 |
| PR 번호 | `gh pr diff <번호>` | `git fetch origin pull/<번호>/head:sasu-pr-<번호>` 뒤 `git show sasu-pr-<번호>:<파일>` | `gh pr view <번호> --json author -q .author.login` |

- 기본 브랜치: `gh repo view --json defaultBranchRef -q .defaultBranchRef.name`, 안 되면 `git symbolic-ref --short refs/remotes/origin/HEAD`.
- 인자가 없는데 변경분이 비면 `git log --oneline -5`를 보여 주고 무엇을 볼지 묻는다.
- 브랜치·PR 리뷰에서는 **작업 폴더 파일을 읽지 않는다.** 지금 체크아웃된 코드와 줄 번호가 다르다. `git checkout`도 하지 않는다 (팀원의 작업 중인 변경을 건드리지 않게).
- 변경분만 보지 말고, 바뀐 파일 전체와 호출하는 곳, 관련 테스트를 같은 버전에서 읽는다.

## 2. 찾기 (ECC code-reviewer 규칙)

심각한 것부터 본다: 보안 → 데이터 손실·버그 → 에러 처리 → 테스트 누락 → 구조 → 가독성.

지적 하나를 쓰기 전에 네 가지를 확인한다. 하나라도 "아니오"면 등급을 내리거나 버린다.
1. 정확한 `파일:줄`을 댈 수 있나?
2. 어떤 입력·상태에서 무엇이 잘못되는지 말할 수 있나?
3. 호출하는 곳, 타입, 테스트까지 읽었나? (한 단계 위에서 이미 막고 있는 경우가 많다)
4. 등급이 과하지 않나?

- 확신 80% 미만이면 말하지 않는다.
- 바뀌지 않은 코드는 심각한 보안 문제가 아니면 지적하지 않는다.
- 비슷한 지적은 하나로 묶는다 ("함수 3개에 같은 문제").
- 저장소 관례와 다른 "일반 모범 사례"는 지적하지 않는다.
- **지적이 0개인 리뷰도 정상이다.** 일부러 만들지 않는다.

### [반드시]는 다른 눈으로 다시 확인

[반드시] 후보가 하나라도 있으면, 쓰기 전에 Agent 도구로 `sasu:review-checker`를 부른다.
스스로 다시 읽는 것으로는 부족하다. 같은 착각(다른 함수의 줄을 읽는 것 등)을 반복한다.

- 넘길 것: 코드를 읽을 곳(PR이면 `sasu-pr-<번호>`와 `origin/<기본 브랜치>`, 브랜치면 그 이름, 아니면 작업 폴더), 그리고 지적마다 번호·`파일:줄`·주장 한 줄·깨지는 입력과 결과.
- 넘기지 않을 것: 왜 그렇게 생각했는지(내 추론). 검증자가 같은 길로 끌려간다.
- 결과에 따라:
  - **확인됨** → 그대로 쓴다.
  - **틀림** → 지운다. 다른 등급으로 남기지도 않는다.
  - **불확실** → [권장]으로 내리고 문제 줄 끝에 "(실행해 봐야 확실함)"을 붙인다.
- 검증자를 부를 수 없으면 그 줄을 `git show`로 직접 다시 열어 확인하고, 판정 아래에 "[반드시]를 독립 확인하지 못했어요" 한 줄을 남긴다.

[권장]·[참고]는 다시 확인하지 않는다 (판정을 막지 않으니 비용을 아낀다).

## 3. 쓰기

```
## 잘한 점
- (구체적으로 1~2개. 없으면 이 칸은 생략)

## 고칠 점
### 1. [반드시] 한 줄 제목 — `파일:줄`
- 문제: 어떤 입력에서 무엇이 깨지는지
- 왜: 이것이 왜 중요한지 (원리 한두 줄)
- 힌트: 어느 방향으로 고치면 되는지. 정답 코드는 쓰지 않는다
- 배울 것: 개념 이름 (예: 경계값, 멱등성, SQL 인젝션)

### 2. [권장] ...
### 3. [참고] ...

## 판정
머지 가능 / 고친 뒤 머지 / 막힘 — 이유 한 줄

## 이번에 익힐 것 하나
(가장 중요한 개념 하나를 3~4줄로 풀어 준다)
```

- 등급: **[반드시]** 버그·보안·데이터 손실 / **[권장]** 유지보수·테스트 / **[참고]** 알아 두면 좋은 것
- 고칠 점은 최대 5개. 넘으면 중요한 5개만 쓰고 "나머지는 이것부터 고친 뒤에 볼게요"라고 쓴다.
- [반드시]가 있으면 판정은 "막힘", [권장]만 있으면 "고친 뒤 머지"를 기본으로 한다.
- 팀원이 "정답 보여 줘", "예시 코드"라고 하면 그 항목만 고친 코드를 보여 준다.

## 4. 기록

[반드시]와 [권장] 항목마다 성장 기록을 남긴다. 주제는 사수 원칙의 고정 목록에서 고른다.

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/sasu.py" lesson --who "<작성자>" --topic "에러 처리" \
  --note "결제 실패를 except 로 삼킴" --source "review:src/pay.py:40"
```

작성자는 1번 표에서 정한 사람이다. 같은 변경분을 다시 리뷰하면 같은 기록은 스크립트가 건너뛴다 ("이미 기록됨").
기록한 뒤 "같은 주제가 이전에도 나왔는지"를 `report`로 확인한다. 반복이면 리뷰 끝에 한 줄로 알려 준다.
